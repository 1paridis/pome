把 `.pome/nursery/blueprint.md` 中的设计方案实现为经过验证的代码。blueprint 决定要实现什么以及范围边界；`.pome/nursery/plan.md` 只是对文件组织、实施顺序和验收方式的参考过程，可以根据代码库现实调整，不能覆盖或缩减 blueprint。

默认持续执行到 blueprint 的设计全部实现并通过验证。用户指定阶段、任务或要求暂停时，只执行指定范围并停在清晰边界。

## 开工前检查

1. `.pome/nursery/plan.md` 不存在：告知用户先用 pome-plot 制定实现计划，到此为止
2. `.pome/nursery/blueprint.md` 不存在：告知用户计划缺少设计依据，先用 pome-seed 补齐设计，到此为止
3. blueprint 仍有遗留问题：告知用户先用 pome-seed 收敛方案，到此为止
4. plan 的依据不是当前 blueprint：告知用户先用 pome-plot 更新参考过程，到此为止
5. plan 与 blueprint 冲突：以 blueprint 为准，忽略冲突的计划内容并在最终报告中说明；若 blueprint 本身存在矛盾或无法实施，再告知用户用 pome-seed 修订设计
6. plan 已全部完成：仍要按 blueprint 核对真实代码和验证结果；只有设计已完整实现时才报告完成

读取适用于当前目录的仓库说明，并查看工作区状态。工作区可以有未提交修改；保留并兼容用户或其他协作者的改动，不还原、不覆盖与当前任务无关的内容。

## 建立执行上下文

开始编码前读取完整 blueprint 和 plan，并以 blueprint 确定实施范围，按需勘察相关代码：

- 确认计划列出的新增、修改、删除文件及其附近实现
- 找到实施范围内最接近的现有功能作为风格参照，识别目录组织、模块边界、命名、类型、公共 API、错误处理、日志、配置、依赖、并发模型、测试和文档约定
- 识别真实依赖，以及 plan 中可复用的阶段、任务和验收步骤
- 建立 blueprint 叶子节点到代码改动和验证的覆盖关系，避免计划遗漏导致设计漏实现
- 检查已勾选任务是否确实存在于当前代码中；明显不一致时以代码和 blueprint 为准，修正错误勾选后再继续

只补足实施所需上下文，不重新做需求设计或另写一份计划。

## 项目风格基线

现有项目的实现方式是默认落地标准。编码前必须读懂足够的相邻代码，不能只根据 blueprint 和 plan 从零设计实现形式。

- 优先复用项目已有的类型、trait/接口、辅助函数、基础设施、依赖和测试工具
- 新文件放入现有职责边界，命名、导出方式、可见性和调用方向与同层模块一致
- 错误传播、日志字段、配置读取、序列化、异步任务、资源管理等横切行为沿用项目现有模式
- 测试放置、fixture、断言风格和命令沿用仓库惯例；除非 blueprint 要求新的验证层级，不另建平行测试体系
- 格式化工具和静态检查以仓库配置为准，不用个人偏好批量改写无关代码

如果项目内存在多种风格，采用实施范围所属模块的局部惯例；共享契约则采用其所有者模块的惯例。只有 blueprint 明确要求改变既有模式时才引入新模式，并把影响限制在必要范围。

## 执行规则

### 按依赖推进

优先参考 plan 的阶段和任务顺序实施；代码库的真实依赖要求不同顺序时直接调整。一个任务包含其正常完成所必需的生产代码、测试、配置和文档改动；不要把代码写完但把直接相关的验证留到最后。

可以调整、合并、拆分或补充 plan 中的步骤，常见情况包括：

- 代码库实际依赖关系要求先完成后列任务
- 合并相邻改动能避免无法构建的中间状态
- plan 遗漏了实现某个 blueprint 叶子节点所需的工作
- plan 中的文件路径、命令或局部实现方式已不符合当前代码库
- 用户明确指定了更小的执行范围

不要跨过尚未满足的依赖，也不要借机做无关重构。

### 遵守设计边界

- blueprint 已确定的行为、数据契约和范围边界直接遵守
- plan 的文件组织和实施路径只作参考；与项目惯例不一致时，以 blueprint 的设计要求和当前代码库风格决定实际落点
- blueprint 要求但 plan 漏列的工作必须补做，包括生产代码、测试、配置、文档、模块导出、依赖锁文件和调用点适配；在最终报告中指出
- 不增加 blueprint 明确排除的能力，不为假设中的兼容性预留代码；plan 中的排除项只有与 blueprint 一致时才有效

若继续实现必须改变 blueprint 的产品或架构决策，停止并让用户回到 pome-seed。仅需重排模块、扩大文件范围或修改验收方式时可以直接调整，因为 plan 是参考过程；记录与 plan 的偏差，不要借调整过程改写 blueprint。

### 保持改动可审查

- 延续相邻模块的代码风格和抽象层级，选择完整实现 blueprint 的最小正确改动
- 不为了逐字照搬 plan 而引入平行架构、重复基础设施或与项目不同的新命名体系
- 修改前读懂调用方和被调用方；共享契约变化时同步处理所有受影响位置
- 对风险与改动范围匹配地增加或更新测试，不删除有效测试来换取通过
- 不执行提交、推送、发布、迁移生产数据或破坏性操作，除非 blueprint 包含且用户明确要求

## 验证与进度

每完成一个任务，运行与该任务直接相关的最小验证。只有同时满足以下条件才把对应 `- [ ]` 改为 `- [x]`：

- 实现及必要测试、配置或文档已经落盘
- 相关验证成功
- 没有已知缺口需要留给该任务处理

每完成一个阶段，参考该阶段的“验收”命令或检查，并根据实际改动补充必要验证。验收成功后勾选验收项，再进入下一阶段。修改 `plan.md` 时可以更新复选框并简要记录实际执行偏差，但不要把 plan 改写成新的设计依据。

验证失败时先定位并修复本次实现造成的问题，然后重跑。若失败来自环境、外部服务或既有缺陷，保留对应任务未勾选，记录具体命令、关键错误和阻塞原因；能独立推进的后续任务可以继续，依赖该阻塞的任务不得越过。

最后参考 plan 规定的项目级验收，并从仓库现有脚本、CI 配置或项目文档中补充与实际改动匹配的格式检查、静态检查、测试和构建，不臆造不存在的命令。

## 中断与恢复

用户暂停、上下文受限或出现无法自行解决的阻塞时：

- 完成正在进行中的最小可验证单元，除非继续操作会造成风险
- 立即把已经验证的任务勾选，未完成或未验证的任务保持未勾选
- 简要报告已完成项、当前阻塞、失败验证和下一个待办

下次继续时重新读取 plan 和工作区状态，从第一个未勾选且依赖已满足的任务恢复，不重复已验证工作。

## 完成与输出

全部任务完成后，以 blueprint 的每个叶子节点做最终覆盖检查，并参考 plan 的代码组织和实施清单查漏补缺；同时检查差异中是否出现明确排除的能力。发现遗漏就补齐并重新验证；发现越界改动则只移除自己引入的越界内容，不触碰既有用户改动。

最终回复只报告执行结果，不粘贴整份计划：

- 完成了哪些阶段和关键行为
- 重要文件或模块变更
- 实际运行的验证及结果
- 对计划的必要补充或偏差
- 未完成的 blueprint 节点与阻塞；全部完成时明确说明设计已完整实现，并报告 plan 的勾选状态

不要宣称未运行的验证已通过，也不要因为大部分功能可用就勾选仍有缺口的任务。
