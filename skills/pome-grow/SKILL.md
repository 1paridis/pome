# pome-grow

生长代码。按 `tasks.md` 逐项把设计落地为实际代码，并把已完成任务的 `- [ ]` 勾选为 `- [x]`。本技能只实现代码和更新勾选状态，不重新规划任务、不修改设计文档、不改写任务内容。

## 输入

从用户明确指定的路径或当前需求上下文定位 `.pome/nursery/`，读取：

- `tasks.md`：待实现的任务清单，顶部来源行决定本阶段的管线与依据。
- 来源设计（始终只读，不得修改）：
  - 开发管线 `> 来源：blueprint.md`：每个叶子含「功能说明」和「技术方案」，实现功能代码。
  - 测试管线 `> 来源：test-case.md`：每个叶子含「前置条件」「输入数据」「执行步骤」「预期结果」，实现自动化测试代码。
- 实际项目代码：项目级说明、依赖配置、目录结构、相关现有实现与测试组织方式。

同一目录存在两个设计文件、或来源行缺失/无法识别时，先询问，不得自行推断管线。

### 输入门禁

实现前先检查输入，任一不过则报告路径与受影响项后停止，不得补写、猜测或重规划：

- `tasks.md` 存在，且顶部只有一条来源说明，能唯一确定管线。
- 来源设计文件存在，且对应管线的叶子字段完整（blueprint 每叶含「功能说明」+「技术方案」；test-case 每叶含四字段）。
- `tasks.md` 的 todo 与来源设计叶子一一对应：一个设计叶子对应一个 todo，无缺漏、无合并、无设计之外的任务。

## 规则

- 每个 todo 就是一个 Markdown checkbox；grow 只把已完成的 `- [ ]` 改为 `- [x]`，不新增、删除、重排或改写任务内容。
- 按 `tasks.md` 顺序逐项实现；一个设计叶子对应一个 todo，不合并叶子，也不实现设计之外的功能。
- 开发管线：综合叶子的「功能说明」和「技术方案」实现功能代码，验证方式以技术方案中「对应的测试与验证方式」为准——方案要求写测试才写，否则不额外新增测试。
- 测试管线：综合用例四字段编写自动化测试代码，实现覆盖该场景的测试；不得改写成人工执行测试的任务，不得虚构测试框架、接口或数据，须贴合项目实际测试技术栈。
- 实现前从任务相关的现有代码与工程配置中归纳代码风格，按相关性检查目录与模块组织、命名、接口形态、类型使用、错误处理、日志、依赖使用、测试结构，以及格式化和静态检查配置；不得用通用偏好代替项目惯例。
- 新增和修改的代码须遵循项目既有风格。优先参考同目录、同模块或同类功能的相邻实现；项目配置规定优先于个别代码样本。设计决定功能和技术约束，项目风格决定具体表达；二者发生实质冲突时先报告并确认，不得擅自偏离任一方。
- 只在完成 todo 所需范围内保持风格一致，不借实现任务之机格式化、重命名或重构无关代码。
- 引用的既有文件、模块和符号必须来自实际代码库；计划创建的文件、模块或符号标注为「新增」；无法从代码库确认的信息列为待确认项，不得以推测代替调查。

## 勾选标准

一个 todo 满足以下两点才勾选为 `- [x]`：

- 实现已落盘到项目实际目录（开发为功能代码，测试为自动化测试代码）。
- 构建/编译通过：开发代码能编译/构建通过（无构建步骤的项目以「无语法错误、可导入、可启动」为准）；测试代码能编译、能被测试框架收集并执行，不因语法、导入或结构错误而崩溃。

测试是否全部通过不作为勾选的硬性门槛。但运行验证时出现的任何失败或告警都须如实报告，不得隐瞒、不得把失败当通过、不得把「验证未跑」说成「验证通过」。

## 历史保护

`tasks.md` 已存在时先完整读取：

- 已勾选的 `- [x]` 视为已完成，grow 从第一个 `- [ ]` 继续实现，不重做已完成任务。
- 若发现已勾选任务对应的实现与当前代码不一致、或用户明确要求重做某任务，报告受影响 todo 后等待用户裁决，不得擅自改动已有实现。
- 只在勾选时更新 checkbox 状态，不改写任务内容；需要调整任务内容或顺序时交由 Plot 处理，grow 不代劳。

## 产物结构

```text
<项目代码文件>             ← 开发/测试实现落盘到项目实际目录
.pome/nursery/tasks.md     ← 已完成的 - [ ] 改为 - [x]
```

grow 不把代码写入 `.pome/nursery/`；代码落在项目实际目录，`nursery` 只承载进行中的工作产物。

## 执行流程

1. 定位 `.pome/nursery/`，读取 `tasks.md`，确认来源行与管线。
2. 执行输入门禁；发现缺失、结构异常、来源不明或 todo 与设计叶子不对应时，报告后停止。
3. 项目调查：读取项目级说明、依赖配置、格式化与静态检查配置、目录结构、相关现有实现与测试组织方式；重点比较同目录、同模块或同类功能的代码，为每个 todo 建立可靠上下文和代码风格基线。
4. 按 `tasks.md` 顺序逐项实现，并遵循已确认的项目代码风格：开发管线按「功能说明」+「技术方案」实现功能代码；测试管线按用例四字段实现自动化测试代码。
5. 每完成一个 todo，执行构建/编译（或测试可运行性）验证，并运行相关测试以确认可执行、如实记录结果；通过则把对应 `- [ ]` 改为 `- [x]`，失败则修复后重验，仍失败则如实报告。
6. 遇到阻塞（设计缺失或矛盾、代码冲突、需求不明等）立即暂停，说明阻塞项与受影响的 todo，等待用户裁决后继续；不猜测、不跳过、不回退修改设计文档或任务内容。
7. 全部完成后自检，并向用户汇报结果。

## 自检

实现结束后逐项自检，任一不过则回退修正：

- 实现完整：每个 todo 要么已勾选且有对应实现，要么明确报告为阻塞/未完成；无遗漏、无越界实现。
- 勾选诚实：只勾选了已实现且构建通过的任务；未把失败或未验证的任务勾选为完成。
- 依据可靠：既有符号来自实际代码库，新增内容有标注，未虚构框架、接口或数据。
- 风格一致：新增和修改的代码符合相关模块的既有组织、命名、接口、错误处理、测试及工具配置惯例，且未产生无关的风格改动。
- 设计受保护：`blueprint.md`、`test-case.md` 未被修改；`tasks.md` 仅变更了 checkbox 状态，任务内容与顺序未动。
