为用户提出的需求设计解决方案，解决方案以设计树的形式组织。先给出一个设计树，对于有问题的节点把问题列出，整个树列出来给用户参考，等用户选择需要讨论的节点。

## 设计树格式

用 markdown 有序嵌套列表表示，每个节点带层级编号（1、1.1、1.2……），讨论时直接用编号定位节点。节点是需求拆解出的功能单元：中间层节点是功能域，只起分组作用；叶子节点是能直接描述实现方案的最小单元。

叶子节点名后的内容二选一，不用额外的状态标记：

- 方案已明确：直接写方案，一句话说清做什么、怎么做
- 有待讨论的问题：用子列表列出问题

节点有没有问题，看它下面有没有问题子列表即可。

以"用户登录"需求为例：

```markdown
1. 用户登录
   1. 登录入口：导航栏右侧登录按钮，点击弹出登录对话框
   2. 登录方式：邮箱+密码登录，暂不做第三方登录
   3. 注册流程
      - 问题：是否需要邮箱验证？影响数据模型和是否引入邮件服务
   4. 密码找回：邮箱重置链接，30 分钟有效，60 秒冷却后可重新发送
   5. 会话管理：JWT，access token 2 小时 + refresh token 14 天，静默续期
   6. 登录安全
      1. 密码存储：bcrypt 加盐哈希
      2. 失败保护：连续 5 次失败锁定 10 分钟，记录失败 IP
```

## 什么算"有问题的节点"

满足任一条，在节点下用子列表列出问题：

- **方向分歧**：存在多个合理但互斥的实现方向，需要用户拍板（写清各方向是什么）
- **信息不足**：缺关键需求信息，给不出方案（写清缺什么、为什么影响方案）
- **技术风险**：方案依赖外部条件（性能、第三方依赖、权限等），需要用户知情确认

除此之外的节点直接给方案。树里大部分节点应该是确定的——如果列问题的节点超过一半，说明需求拆得太粗，先重新拆分再出树。

## 讨论循环

用户用编号指定一个列有问题的节点（如"讨论 1.2"）后：

1. 给出 2-3 个候选方案，每个附一句话理由和适用场景，标注你推荐哪个、为什么
2. 用户选择后，把选定方案写回该节点、替换掉问题子列表，同时记录这条决策：节点编号与名称、备选方案、用户的选择、理由，并立即更新 blueprint 文件（设计树中的该节点 + 决策记录表追加一行）
3. 不要重新显示整棵树，等待用户选择下一个要讨论的节点

## 完成与输出

- 树上没有列出问题的节点时，主动告知设计完成，并完整展示最终设计树请用户做最后确认（长讨论后用户需要重新看到全貌）
- 用户中途说"先到这里/先输出"时照办，未解决的节点原样写入遗留问题
- 给出设计树时就写入 `.pome/nursery/blueprint.md`：目录不存在则自动创建。文件已存在且内容属于别的需求时，先问用户覆盖还是另存。

blueprint.md 按以下模板输出：

```markdown
# 设计方案：<需求名称>

> 日期：YYYY-MM-DD

## 需求摘要

<两三句话，用户原始诉求的收敛表述>

## 设计树

<最终设计树，格式同上>

## 决策记录

| 节点 | 备选方案 | 选择 | 理由 |
| ---- | -------- | ---- | ---- |
| 1.3 注册流程 | 邮箱验证 / 免验证 | 邮箱验证 | 需确认邮箱真实性，已有邮件服务可用 |

## 遗留问题

<未讨论的节点及其问题，没有则删除本节>
```
