# pome-seed

播种需求。将一个需求拆解为一棵功能设计树，并为每个叶子节点写出技术设计，二者共同落在一份 `blueprint.md` 中。

## 输入

进入 seed 的数据是一个需求，来源两种：

1. 用户直接提出的需求
2. 进行中的历史产物：`nursery` 下已存在该需求的 `blueprint.md`。读取现有内容并等待用户明确指令，不得自行推断此前进度、补齐未完成部分或从头重写

根节点由两部分组成：

- 简要标题：对需求的一句话总结
- 补充说明：对根节点需求的补充描述

## 拆解规则

以需求为根，仅在有助于澄清业务边界时拆分，并优先保持结构浅、节点少。节点能够独立表达一项用户可感知或业务可验收的功能时即停止拆分；不得继续拆成控件、字段、单次交互、代码模块或实现步骤。访谈中的决策依赖只影响提问顺序，功能树只表达功能从属关系。

通过多轮访谈确定功能树。每轮提出一组前置决策均已确定的高优先级问题，原则上不超过 5 个；为问题编号并给出建议答案和简要理由，用户可以整组接受或逐项调整。有依赖的问题留到后续轮次，低风险细节采用合理默认值并在审查时说明。

每轮答复后更新功能树；上游决策变化时，重新确认受影响的下游决策。当功能已明确，且没有阻塞问题时结束访谈；非阻塞假设留到功能树审查时整体确认。

### 拆解门禁

每次拆分必须同时满足以下门禁，任一不满足即停止拆分或回退合并：

- **树高度限制**：根节点计为第 1 层，功能树不得超过 4 层。若 4 层内仍无法清晰表达需求，停止拆解并由用户调整。
- **子节点数量限制**：同一父节点下的直接子节点原则上不超过 7 个。

## 阶段一：功能设计

产出 `.pome/nursery/<需求简称>/blueprint.md`：

- 用 Markdown 多级标题表示树的层级：根节点为 `#`，第二层为 `##`，以此类推，标题层级 = 树的深度
- 节点标题只写功能名称，不添加用于排序的数字、字母或点分序号前缀
- 根节点的补充说明写在根标题下方
- 分支节点：只有标题，不写说明
- 叶子节点：标题下方使用「功能说明」小节，简洁说明该功能做什么

示例：

```markdown
# 需求标题

> 根节点需求的补充说明

## 子功能 A

**功能说明**

简洁说明该功能做什么。

## 功能分组

### 叶子功能 A

**功能说明**

简洁说明该功能做什么。

### 深层功能分组

#### 四层叶子功能

**功能说明**

简洁说明该功能做什么。
```


### 阶段一门禁

- **标题与层级一致**：标题层级必须准确表达节点在功能树中的深度，不得用加粗正文或列表伪造树节点。
- **同级标题唯一**：同一父节点下的子节点标题不得重复；不同分支出现同名节点时，引用节点须使用从共同祖先开始的标题路径。
- **叶子必有说明**：每个叶子节点都必须写功能说明；任何分支节点都不得出现说明文字。
- **说明只写「做什么」**：功能说明不得涉及实现（不写「如何做」）。

### 审查暂停

功能设计完成后，暂停并把功能树交给用户审查，不要直接进入阶段二。用户可以：

- 批准整棵功能树，继续阶段二
- 使用节点标题指定要讨论、修改、增删或重新拆解的节点；存在同名节点时，使用标题路径，如「功能分组 > 叶子功能 A」

在用户确认前，不得开始技术设计。用户每次提出修改后，回到功能树修正对应部分并再次暂停，直到用户确认继续。

## 阶段二：技术设计

对功能设计中的每一个叶子节点做开发设计，把技术方案补写在对应叶子节点的「技术方案」小节内，仍落盘于 `.pome/nursery/<需求简称>/blueprint.md`。

### 项目调查

开始技术设计前，先读取项目级说明、依赖配置、目录结构和与需求相关的现有实现，确认：

- 项目使用的语言、框架与依赖
- 相关模块、入口、接口与数据结构
- 可以复用的现有实现和项目约定
- 现有测试的组织方式
- 需求可能影响的调用链与持久化数据

技术方案中引用的既有文件、模块和符号必须来自实际代码库。对于计划创建的文件、模块或符号，明确标注为「新增」；无法从代码库确认的信息列为待确认项，不得以推测代替调查。

叶子节点的最终形态：

```markdown
### 叶子功能

**功能说明**

简洁说明该功能做什么。

**技术方案**

实现思路、涉及文件/模块、关键接口或数据结构、注意点……
```

技术方案正文示例：

```markdown
### 用户登录

**功能说明**

支持邮箱 + 密码登录，失败提示具体原因。

**技术方案**

在 `auth/login.py` 新增 `login(email, password)`，调用既有的 `User.query_by_email` 校验密码哈希，成功则签发 JWT（复用 `utils/jwt.py`），失败返回对应错误码。注意密码比对须用常量时间比较，避免时序攻击。
```

技术方案应按叶子的实际复杂度覆盖以下适用内容：

- 复用、修改或新增的文件与模块
- 主要调用流程与职责边界
- 接口、数据结构、状态或持久化变化
- 错误处理、权限、安全与并发注意点
- 兼容性、数据迁移或配置变化
- 对应的测试与验证方式

简单叶子无需机械填写所有项目，但方案必须具体到足以支持后续任务规划，不得只写「新增接口」「修改逻辑」等空泛表述。

### 阶段二门禁

- **每个叶子都有技术方案**：所有叶子节点都须补写「技术方案」小节，不得遗漏。
- **不改功能设计**：补写技术方案时不得反向修改功能设计（功能说明、树结构）。若发现功能设计不合理，暂停整个阶段二，说明受影响节点并请求用户确认；得到确认后回到阶段一修正，重新通过功能树审查后再继续技术设计。
- **贴合实际技术栈**：技术方案必须贴合项目实际技术栈，不得虚构不存在的依赖、框架或模块。
- **方案可以落地**：技术方案须提供足以支持后续任务规划的具体信息，并明确区分既有实现、新增内容和待确认项。

## 产物结构

`<需求简称>` 采用 kebab-case 英文，如 `user-login`。

```
.pome
└── nursery
    └── <需求简称>
        └── blueprint.md
```

## 执行流程

1. 确认需求：确定根节点的简要标题和补充说明；优先根据标题生成 kebab-case 英文 `<需求简称>`，仅在名称存在歧义或目录冲突时请用户确认
2. 断点续做检查：看 `.pome/nursery/<需求简称>/blueprint.md` 是否已存在。不存在则继续新建设计；存在则读取文件、告知用户发现历史产物并停止，等待用户明确指令。不得自行检查完成度、推断继续点、补齐、重写或改变已有内容
3. 功能设计：逐层拆解，生成 `blueprint.md`
4. 审查暂停：功能设计完成后暂停，请用户审查功能树；用户可批准继续或指定节点讨论修改
5. 项目调查：用户确认功能树后，读取项目约定、依赖和相关代码，为技术设计建立可靠上下文
6. 技术设计：基于实际代码，为功能设计中的每个叶子节点补写技术方案
7. 最终交付：完成门禁自检，向用户报告产物路径、叶子节点数量、已完成技术方案数量和所有待确认项

### 流程门禁

- 阶段二必须在阶段一完成后进行。
- 每阶段完成后自检对应门禁，未通过则回退修正，不得进入下一阶段。
- 产物必须落盘到 `.pome/nursery/<需求简称>/` 下，文件名为 `blueprint.md`。
- 历史 `blueprint.md` 的已有内容受保护；除非用户明确指定继续或修改，不得对文件落盘变更。
