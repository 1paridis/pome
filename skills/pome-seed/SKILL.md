# pome-seed

播种需求。把需求收敛为一棵功能设计树，并为每个叶子写出技术设计，落在一份 `blueprint.md` 中。

## 输入

进入 seed 的数据是一个需求，来源两种：

1. 用户直接提出的需求
2. 进行中的历史产物：`nursery` 下已存在该需求的 `blueprint.md`。读取现有内容并等待用户明确指令，不得自行推断此前进度、补齐未完成部分或从头重写

根节点由三部分组成：

- 简要标题：对需求的一句话总结
- 补充说明：对根节点需求的补充描述
- 范围：本次需求覆盖与不覆盖的功能面（见下）

## 范围

拆解前先明确横向边界，避免功能树越扩越大。范围由用户澄清或从需求推断；推断部分须经用户确认。

- **包含（in-scope）**：本次要覆盖的功能面。
- **不包含（out-of-scope）**：相邻、相关但明确不做、留待后续的功能。
- **边界模糊处**：先问，不默认纳入也不默认排除。

拆解过程中，每个新节点都要能回答「它属于本次范围吗」；答不上来就停下确认，不顺着惯性往下铺。范围的取舍本身也是访谈内容的一部分。

## 拆解

拆解只为一个目的服务：把需求收敛成可独立验收的功能单元。要不要拆、拆到哪，只有一个标准——业务必要性。

- 只有「不拆开，边界就说不清」时才拆；一旦节点已能独立表达一项用户可感知或业务可验收的功能，立即停止。
- 不继续拆成控件、字段、单次交互、代码模块或实现步骤；宁可少拆一层，也不为凑结构而拆。

通过多轮访谈确定功能树。每轮提出一组前置决策均已确定的高优先级问题，原则上不超过 5 个；为问题编号并给出建议答案和简要理由，用户可整组接受或逐项调整。有依赖的问题留到后续轮次，低风险细节采用合理默认值并在审查时说明。

每轮答复后更新功能树；上游决策变化时，重新确认受影响的下游决策。当功能已明确且没有阻塞问题时结束访谈；非阻塞假设留到功能树审查时整体确认。

## 阶段一：功能设计

产出 `.pome/nursery/blueprint.md`。生成前先读 `references/blueprint-format.md`，确认标题层级、叶子「功能说明」写法与结构门禁；自检时对照其中的清单逐条核对。

阶段一门禁：

- **范围一致**：树的每个节点都在已确认范围内，无越界扩展。
- **结构正确**：标题层级表达树深，叶子都有功能说明，分支只有标题（逐条清单见 references）。
- **说明只写「做什么」**：功能说明不涉及实现。

### 审查暂停

功能设计完成后暂停，把功能树交给用户审查，不要直接进入阶段二。用户可以：

- 批准整棵功能树，继续阶段二
- 使用节点标题指定要讨论、修改、增删或重新拆解的节点；存在同名节点时，使用标题路径，如「功能分组 > 叶子功能 A」

在用户确认前，不得开始技术设计。用户每次提出修改后，回到功能树修正对应部分并再次暂停，直到用户确认继续。

## 阶段二：技术设计

对每个叶子节点做开发设计，把技术方案补写在对应叶子的「技术方案」小节内，仍落盘于 `.pome/nursery/blueprint.md`。

### 项目调查

开始技术设计前，先读取项目级说明、依赖配置、目录结构和与需求相关的现有实现，确认：

- 项目使用的语言、框架与依赖
- 相关模块、入口、接口与数据结构
- 可以复用的现有实现和项目约定
- 现有测试的组织方式
- 需求可能影响的调用链与持久化数据

技术方案中引用的既有文件、模块和符号必须来自实际代码库；计划创建的文件、模块或符号标注为「新增」；无法确认的信息列为待确认项，不得以推测代替调查。

技术方案按叶子实际复杂度覆盖：复用/修改/新增的文件与模块、主要调用流程与职责边界、接口与数据结构变化、错误处理与安全并发注意点、兼容性与迁移、对应的测试与验证方式。简单叶子无需机械填满，但方案必须具体到足以支撑后续任务规划。

### 阶段二门禁

- **每个叶子都有技术方案**：不得遗漏。
- **不改功能设计**：补写技术方案时不得反向修改树结构、功能说明或范围。若发现功能设计不合理，暂停整个阶段二，说明受影响节点并请求确认；确认后回到阶段一修正，重新通过审查后再继续。
- **贴合实际技术栈、方案可落地**：不虚构依赖或模块，明确区分既有实现、新增内容和待确认项。

## 产物结构

```
.pome
└── nursery
    └── blueprint.md
```

## 执行流程

1. 确认需求：确定根节点的简要标题、补充说明和范围。
2. 断点续做检查：看 `.pome/nursery/blueprint.md` 是否已存在。不存在则继续新建设计；存在则读取、告知用户发现历史产物并停止，等待明确指令。不得自行检查完成度、推断继续点、补齐、重写或改变已有内容。
3. 功能设计：先定范围，再逐层拆解，生成 `blueprint.md`。
4. 审查暂停：功能设计完成后暂停，请用户审查功能树；用户可批准继续或指定节点讨论修改。
5. 项目调查：用户确认功能树后，读取项目约定、依赖和相关代码，为技术设计建立可靠上下文。
6. 技术设计：基于实际代码，为每个叶子补写技术方案。
7. 最终交付：完成门禁自检，报告产物路径、叶子节点数量、已完成技术方案数量和所有待确认项。

### 流程门禁

- 阶段二必须在阶段一完成后进行。
- 每阶段完成后自检对应门禁，未通过则回退修正。
- 产物必须落盘到 `.pome/nursery/` 下，文件名为 `blueprint.md`。
- 历史 `blueprint.md` 的已有内容受保护；除非用户明确指定继续或修改，不得落盘变更。
