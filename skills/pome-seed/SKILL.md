# pome-seed

播种需求。将一个需求拆解为「功能设计」与「技术设计」两份产物。

## 输入

进入 seed 的数据是一个需求，来源两种：

1. 用户直接提出的需求
2. seed 的历史产物（已有功能设计的根节点，作为新一轮拆解的输入）

根节点由两部分组成：

- 简要标题：对需求的一句话总结
- 补充说明：对根节点需求的补充描述

## 拆解规则

以需求为根，按树状结构展开：

- 每次只拆一层
- 整个树就是一个目录结构
- 对拆出的一层节点，以广度优先（BFS）方式，每次一个节点拆出其下一层节点
- 直到该节点无法被分割为止

「无法被分割」的判定：该节点已经是一个可独立、原子实现的功能点，无需再往下拆。

### 拆解门禁

拆解必须同时满足以下门禁，任一不满足即停止拆分或回退修正：

- **树高度 ≤ 3 层**：根为第 1 层，叶子最多到 `###`（三级标题）。若某个功能仍需第 4 层才能表达，说明根节点范围过大，应回退缩小根节点范围，而不是继续深挖。
- **不过度拆分**：叶子节点必须是「可独立交付、有完整语义的功能单元」，而非实现步骤或琐碎动作。判定标准：拆出的叶子对业务/用户是否仍有独立意义；若只是把一个功能机械地切成几个动作，则停止拆分。
- **子节点数量受限**：同一父节点下的子节点建议 3~7 个；超过 7 个通常意味着拆分粒度过细，应归并或上提。

## 阶段一：功能设计

产出 `.pome/<需求简称>/orchard.md`：

- 用 Markdown 多级标题表示树的层级：根节点为 `#`，第二层为 `##`，以此类推，标题层级 = 树的深度
- 每个标题使用「点分序号 + 标题」编号：根为 `1`，子节点为 `1.1`、`1.2`，孙节点为 `1.1.1`，以此类推
- 根节点的补充说明写在根标题下方
- 分支节点：只有标题，不写说明
- 叶子节点：标题下方写一段简洁的功能说明

示例：

```markdown
# 1 需求标题

> 根节点需求的补充说明

## 1.1 子功能 A

### 1.1.1 叶子功能

简洁的功能说明。

### 1.1.2 叶子功能

简洁的功能说明。

## 1.2 子功能 B

### 1.2.1 叶子功能

简洁的功能说明。
```

### 讨论提问

拆解过程中若需向用户澄清需求，可一次性提出多个问题，但同一批提出的多个问题之间不要互相影响：各问题独立作答，一个问题的答案不改变其他问题的答案。

### 阶段一门禁

- **编号与层级一致**：点分序号段数必须等于该节点的深度（根 `1` 一段、子 `1.1` 两段、孙 `1.1.1` 三段）。
- **叶子必有说明**：每个叶子节点都必须写功能说明；任何分支节点都不得出现说明文字。
- **说明只写「做什么」**：功能说明不得涉及实现（不写「如何做」）。

## 阶段二：技术设计

对功能设计中的每一个叶子节点做开发设计。产出 `.pome/<需求简称>/cultivation.md`：

- 每个叶子节点对应一个 `##` 二级标题，标题格式为「叶子节点在功能设计中的序号 + 叶子标题」
- 标题下方写技术方案正文：实现思路、涉及文件/模块、关键接口或数据结构、需要留意的点等

示例：

```markdown
# 技术设计

## 1.1.1 叶子功能

技术方案正文……

## 1.1.2 叶子功能

技术方案正文……

## 1.2.1 叶子功能

技术方案正文……
```

### 阶段二门禁

- **叶子一一对应**：技术设计的标题须与功能设计的叶子节点完全一致，不新增、不遗漏、不合并。
- **不改功能设计**：技术设计不得反向修改功能设计；若发现功能设计不合理，应先回阶段一修正再继续。
- **贴合实际技术栈**：技术方案必须贴合项目实际技术栈，不得虚构不存在的依赖、框架或模块。

## 产物结构

```
.pome
└── <需求简称>
    ├── orchard.md
    └── cultivation.md
```

## 执行流程

1. 确认需求：确定根节点的简要标题与补充说明
2. 功能设计：按 BFS 逐层拆解，生成 `orchard.md`
3. 技术设计：针对功能设计中的每个叶子节点，生成 `cultivation.md`

### 流程门禁

- 阶段二必须在阶段一完成后进行。
- 每阶段完成后自检对应门禁，未通过则回退修正，不得进入下一阶段。
- 产物必须落盘到 `.pome/<需求简称>/` 下，文件名固定为 `orchard.md` 与 `cultivation.md`。
