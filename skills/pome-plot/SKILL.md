# pome-plot

把 `blueprint.md` 或 `test-case.md` 整理为简单的 Markdown todo 清单 `tasks.md`，供后续阶段逐项实现和勾选。本技能只规划任务，不写实现代码、不执行或勾选任务、不估算工时。

## 输入

从用户明确指定的路径或当前需求上下文定位 `.pome/nursery/`，读取其中一种设计产物：

- 开发管线：已完成的 `blueprint.md`，每个叶子功能生成一个开发实现 todo。
- 测试管线：已批准的 `test-case.md`，每个叶子测试用例生成一个测试实现 todo。

同一目录同时存在两个设计文件时，根据用户明确指定的管线或文件选择；用户未指定时先询问，不得自行推断。`blueprint.md` 和 `test-case.md` 始终只读，不得修改。

### 输入门禁

生成任务前先检查输入：

- `blueprint.md` 的每个叶子必须同时包含「功能说明」和「技术方案」，且没有会阻止任务落地的待确认项。
- `test-case.md` 的每个叶子必须同时包含「前置条件」「输入数据」「执行步骤」和「预期结果」，阻塞项已经清零。
- 当前对话应能确认 `blueprint.md` 已完成 Seed 最终交付，或 `test-case.md` 已获用户批准；无法确认时，先询问用户是否以当前文件版本作为本次规划输入，不得根据文件存在推断其状态。

发现缺失字段、结构异常或阻塞项时，报告文件路径和受影响的叶子标题路径后停止。不得在 Plot 中补写、修复或猜测源设计。

## 已有任务保护

`tasks.md` 已存在时先完整读取，再根据用户意图处理：

- **定向调整**：用户指定修改某些 todo 的内容或顺序时，只改授权范围；未修改任务的内容和 checkbox 状态保持不变，完成标准发生变化的任务恢复为 `- [ ]` 并报告。
- **重新生成**：只有用户明确要求重新生成或确认覆盖后才重建清单；仅为内容和完成标准都未变化的任务保留原 checkbox 状态，已变化或无法可靠对应的任务恢复为 `- [ ]`，并报告状态变化。
- **来源切换**：现有文档来源与本次输入不同，或来源无法确认时，说明 `tasks.md` 一次只承载一条管线的任务，取得明确替换授权前不得写入。

用户只要求执行任务、继续实现或把任务标为完成时，不进入任务规划，也不重写 `tasks.md`；这些操作属于后续阶段。

## 规则

- 每个任务就是一个 Markdown checkbox：`- [ ] <任务>` 或保留下来的 `- [x] <任务>`。
- 一个设计叶子对应一个 todo，不合并多个叶子，也不添加设计之外的任务。
- todo 用一句话写清对应功能或场景、要实现什么以及达到什么可判定结果，保持简短、可执行。
- 开发 todo 综合叶子的「功能说明」和「技术方案」编写，覆盖方案中与该叶子直接相关的实现与验证。
- 测试 todo 综合用例的四个字段编写为“实现覆盖该场景的测试并验证预期结果”，不得改写成人工执行测试的任务，也不得虚构测试框架、接口或数据。
- 测试任务默认保持设计顺序，也可按已明确的风险优先级排序，但顺序不得表示用例间存在状态依赖。
- 文档顶部必须且只能记录一个来源说明：`> 来源：blueprint.md` 或 `> 来源：test-case.md`；不为每个 todo 添加任务 ID、来源、依赖、产出物、完成定义或注意事项等字段。
- 遇到会阻止任务落地的模糊事项，先向用户确认，不把猜测写成 todo。

## 产物结构

```text
.pome/nursery/tasks.md
```

开发任务示例：

```markdown
# 任务清单

> 来源：blueprint.md

- [ ] 实现用户登录，正确凭据返回 JWT，错误凭据返回对应错误码，并通过相关测试。
- [ ] 登录页接入登录接口，登录成功后跳转首页，失败时显示错误提示。
```

测试任务示例：

```markdown
# 任务清单

> 来源：test-case.md

- [ ] 实现有效账号登录测试，按用例准备并提交有效凭据，验证登录成功并进入首页。
- [ ] 实现错误密码登录测试，按用例提交错误密码，验证页面提示密码错误且不跳转。
```

后续执行阶段只把完成任务的 `- [ ]` 改为 `- [x]`，不改写任务内容；需要调整任务内容或顺序时重新使用 Plot。

## 执行流程

1. 根据用户指定路径或当前上下文定位 `.pome/nursery/` 目录。
2. 检查目录中的设计文件；两者共存且用户未指定输入时，询问选择开发管线还是测试管线。
3. 完整读取所选设计，执行输入门禁；状态无法确认或存在阻塞时暂停询问。
4. 检查 `tasks.md` 是否存在；存在则读取来源、任务内容和 checkbox 状态，确定是定向调整、重新生成还是来源切换，并在需要时先取得授权。
5. 按标题树顺序列出所有设计叶子，将每个叶子改写为一个简短 todo，并按对应管线的排序规则排列。
6. 写入或按授权范围更新 `tasks.md`；重新生成时按已有任务保护规则处理 checkbox 状态。
7. 自检设计叶子与 todo 是否一一对应、来源是否正确、每项是否可执行且可判断完成，并确认没有修改源设计或未授权内容。
8. 展示任务清单，请用户确认；用户要求调整时只修改指定 todo，并再次自检。

用户确认后，报告产物路径、来源文件、todo 总数，以及保留、重置或移除的 checkbox 状态数量。
