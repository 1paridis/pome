把 `.pome/nursery/blueprint.md` 的设计方案转成一份可执行的实现计划。计划不是 blueprint 的复述：blueprint 按功能域组织，回答"做什么"；计划按依赖顺序组织，回答"先改哪个文件、每一步怎么验收"。计划必须落在真实的代码库上，动笔前先勘察、先跑基线。

## 开工前检查

1. `.pome/nursery/blueprint.md` 不存在：告知用户先用 pome-seed 完成需求设计，到此为止
2. blueprint 带遗留问题（未收敛节点）：警告这些节点方案未定、计划将按当前写法展开，逐条列出请用户确认后再继续
3. `.pome/nursery/plan.md` 已存在：问用户是修订原计划还是重新规划并覆盖

## 代码库勘察

计划里出现的每个文件路径都要有依据，先勘察再动笔：

- 项目类型与工具链：从 Cargo.toml / package.json / go.mod / pyproject.toml 等探测构建、测试、lint 命令
- 目录结构：blueprint 涉及的现有模块（接入层、配置、日志等）在哪里，新代码放在哪一层才符合现有组织方式
- 现有约定：错误处理、日志、配置加载、测试各用什么模式，新代码沿用现有风格而不是另起炉灶

勘察只读不写，不要顺手修改任何文件。

## 基线检查

- 探测到测试命令就实际执行，结果记入"当前基线"（如 `cargo test：24 个单元测试通过`）
- 探测不到测试命令或测试失败：如实告知用户，"当前基线"写明"未验证"及原因，不因此中止规划
- 记录 git status 里已有的未提交改动，提醒实施时不得覆盖这些无关改动

## 制定计划

### 总体策略

两三句说清骨架：分层思路、哪些逻辑保持同步纯函数以便单测、异步与 IO 的边界在哪、数据从输入到输出怎么流。blueprint 划定的范围边界（首版不做什么）原样带进来，不悄悄扩大也不遗漏。

### 代码组织

分新增、修改两组：新增文件给路径加一句话职责，修改文件给路径加改动要点。路径必须来自勘察结果，不发明不存在的文件。

### 实施顺序

把设计树的功能域重排为依赖递进的阶段，排布原则：

- 被依赖的先做：配置与数据模型通常最先，接入与集成通常最后
- 一个阶段对应一次可提交的工作量：独立可测、可 review，不依赖尚未完成的下一阶段
- 纯逻辑（计算、规则、状态机）与异步设施（actor、通道、调度）分阶段，纯逻辑先落地并配单测
- blueprint 的验证方案拆进相关阶段的验收，不留到最后集中补测
- 收尾阶段跑通项目全部检查（测试、lint、格式化）

每个阶段是一份勾选任务清单：阶段保持编号，任务用 `- [ ]` 勾选框，实施时完成一项勾一项，进度对用户可见。任务说清做什么、怎么做；最后一项固定为"验收"，用可判定的语句写（如"参考 YAML 可成功加载；根级错误和单相机错误具有不同处理结果"），不写"完成开发"这类空话。

### 建议提交拆分

按阶段给 conventional commits 风格的提交列表，一个提交对应一个或几个相近阶段，标注对应的阶段编号。提交项同样用 `- [ ]` 勾选框，提交完成后勾选。

### 实施节奏

每个提交单元是一个自然的审查点，这条规则写进计划本身（实施会话往往是全新上下文，只看得到 plan.md）：

- 任务与提交项逐项勾选：完成一个任务勾一个，提交一个勾一个
- 每个提交单元完成并通过自查（测试、lint、格式化）后暂停，向用户展示改动要点，待其审查确认后再提交并继续下一单元
- 不连续完成多个提交单元后一次性提交，避免 diff 过大难以审查；用户明确要求连续推进时除外

### 当前基线

基线检查的结果与未提交改动。

## 两条红线

- 不翻案：决策记录里已定的选择直接遵守；计划与决策冲突时改的是计划
- 冲突显式化：勘察发现 blueprint 与代码库现实相悖（引用不存在的依赖、与现有架构冲突）时，在对应阶段标注冲突与适配做法，请用户确认计划时一并拍板，不静默改掉设计

## 确认与落盘

展示草稿前先自查：设计树每个叶子节点都被某个阶段覆盖，决策记录每一条都被遵守，有缺口先补齐再展示。用户提修改意见就迭代，确认后写入 `.pome/nursery/plan.md`（目录不存在则创建），落盘内容与最终展示一致。

plan.md 按以下模板输出：

```markdown
# 实现计划：<需求名称>

> 日期：YYYY-MM-DD
> 依据：.pome/nursery/blueprint.md

## 总体策略

<两三句：分层思路、同步与异步边界、可测性策略、范围边界>

## 代码组织

新增：

- `<路径>`：<一句话职责，没有则删除本节>

修改：

- `<路径>`：<改动要点，没有则删除本节>

删除：

- `<路径>`：<删除内容，没有则删除本节>

## 实施顺序

1. <阶段名>
   - [ ] <任务：做什么、怎么做>
   - [ ] <任务>
   - [ ] 验收：<可判定的验收标准>
2. <阶段名>
   - [ ] ...

## 建议提交拆分

- [ ] `feat(<scope>)：<subject>`（对应阶段 N）
- [ ] ...

## 实施节奏

- 实施时逐项勾选：完成一个任务勾一个，提交一个勾一个
- 每个提交单元完成并通过自查（测试、lint、格式化）后暂停，向用户展示改动要点，待确认后再提交并继续下一单元；不连续完成多个提交单元后一次性提交

## 当前基线

<测试命令与结果、未提交改动；未验证时写明原因>
```
