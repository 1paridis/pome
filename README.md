# pome

> **pome** —— 一枚石榴，也是一套面向 AI 辅助开发的流程化 skill 集合。
>
> 有人说石榴是世界上最慷慨的果实：剥开坚硬的外壳，它把整整一个秋天都藏在了怀里——千颗籽实，颗颗红润，像被小心收藏起来的星。pome 便是这样一枚果实，将「需求开发」与「测试开发」两条流程，凝结成一粒粒独立而可复用的阶段 skill，彼此紧偎，同生一果。
>
> 而最动人的，是石榴的籽，本来就是种子。果实落进土里，不是结束，而是另一场等待的开始。pome 循着同样的心意：**播种（Seed）→ 规划（Plot）→ 生长（Grow）→ 收割（Reap）**——每一次收割，都不是告别，只是把下一次的春天，悄悄埋进了土里。

## 概览

pome 规划提供 5 个 skill，覆盖两条完整流程：

| Skill | 角色 | 适用流程 |
|---|---|---|
| `pome-seed` | 需求设计起点 | 开发流程 |
| `pome-trial` | 测试设计起点 | 测试流程 |
| `pome-plot` | 任务规划（共用） | 开发 + 测试 |
| `pome-grow` | 开发/测试实现（共用） | 开发 + 测试 |
| `pome-reap` | 归档（共用） | 开发 + 测试 |

当前已实现 `pome-seed` 和 `pome-trial`；其余 skill 仍在规划中。

## 流程

### 需求开发流程

| 阶段 | 英文名 | 含义 | Skill |
|---|---|---|---|
| 需求设计 | **Seed** | 播种需求 | `pome-seed` |
| 任务规划 | **Plot** | 规划地块，双关「规划」 | `pome-plot` |
| 开发实现 | **Grow** | 生长，开发实现 | `pome-grow` |
| 归档 | **Reap** | 收割归档 | `pome-reap` |

流程顺序：`pome-seed` → `pome-plot` → `pome-grow` → `pome-reap`

### 测试开发流程

| 阶段 | 英文名 | 含义 | Skill |
|---|---|---|---|
| 测试设计 | **Trial** | 试验、测试；农业中「试验田」 | `pome-trial` |
| 任务规划 | **Plot** | 规划地块，双关「规划」 | `pome-plot` |
| 测试实现 | **Grow** | 生长，测试开发实现 | `pome-grow` |
| 归档 | **Reap** | 收割归档 | `pome-reap` |

流程顺序：`pome-trial` → `pome-plot` → `pome-grow` → `pome-reap`

## 词汇说明

两条流程共用 `Plot / Grow / Reap` 三个阶段，仅起始阶段不同：开发流程以 `Seed`（播种需求）开始，测试流程以 `Trial`（试验田）开始。

| 词汇 | 角色 | 适用流程 |
|---|---|---|
| **Seed** | 需求设计起点 | 开发流程 |
| **Trial** | 测试设计起点 | 测试流程 |
| **Plot** | 任务规划（共用） | 开发 + 测试 |
| **Grow** | 开发/测试实现（共用） | 开发 + 测试 |
| **Reap** | 归档（共用） | 开发 + 测试 |

## 产物

已实现的起始 skill 将产物落盘到 `.pome/nursery/<需求简称>/` 目录（`nursery/` 存放当前进行中的产物；`<需求简称>` 采用 kebab-case 英文，如 `user-login`）：

| 文件 | 内容 |
|---|---|
| `orchard.md` | 以无编号的 Markdown 多级标题保存功能设计树；分支节点只保留标题，叶子节点包含「功能说明」，用户确认功能树后再补写「技术方案」 |
| `test-case.md` | 以无编号的 Markdown 多级标题保存测试设计树；分支节点组织测试范围或场景，叶子节点是包含前置条件、输入数据、执行步骤和预期结果的测试用例 |

### `pome-seed` 设计流程

1. 确认需求标题与补充说明，并检查是否存在历史 `orchard.md`；发现历史产物时先停止，等待用户明确继续或修改。
2. 通过多轮访谈逐步确定功能树。每轮优先询问前置决策已确定的高优先级问题，原则上不超过 5 个。
3. 功能树保持浅而精：根节点计为第 1 层，最多 4 层；同一父节点的直接子节点原则上不超过 7 个；节点达到用户可感知或业务可验收的功能粒度后停止拆分。
4. 功能设计完成后暂停，由用户审查功能树；确认前不进入技术设计。
5. 用户确认后调查项目的实际技术栈、相关实现与测试约定，再为每个叶子节点补写可落地的技术方案。

### `pome-trial` 设计流程

1. 确认测试目标并检查历史 `test-case.md`；发现历史产物时先停止，在用户明确指示前不得修改。
2. 结合最小范围澄清或项目调查执行复杂度判断；简单、单路径且低风险的验证默认不创建专项测试设计。
3. 通过多轮访谈明确测试范围、风险、环境和覆盖策略，每轮原则上不超过 5 个高优先级问题。
4. 将复杂测试需求拆解为无固定层数的测试设计树；分支节点组织范围或场景，叶子节点是可独立执行和判定的测试用例。
5. 每个用例写明前置条件、输入数据、执行步骤和预期结果；设计完成后暂停，由用户审查批准。
